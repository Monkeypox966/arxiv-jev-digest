# 运维与恢复

## 日常检查

在 Actions 查看 Daily arXiv Digest 的运行结果和自动生成的运行摘要。每次处理记录 `health.json`、`usage.json`，失败时也写出。发送模式失败可按 `notifications.email_on_failure` 向原收件人发异常通知；预览、inspect 永不发邮件。SMTP 自身故障时异常信也可能发不出，GitHub 失败记录仍是必要的第二条检查渠道。

- HTTP 401 / 403：检查相应 Secret、模型权限和服务地址。
- HTTP 402：检查服务商额度。
- HTTP 429 / 5xx：系统会有限重试，耗尽后失败，稍后重跑。
- 候选超过上限：减少分类或窗口，或提高 `max_candidates`。不会静默截断。
- 摘要 JSON 不完整：检查模型是否支持 JSON Output，或提高 max_tokens。
- SMTP 登录失败：核对服务器、安全模式、用户名与授权码。
- 待确认发送：先检查收件箱和垃圾箱，再执行 resolve。
- 预算耗尽：运行保持失败、不发日报；成功调用已缓存。检查 `usage.json`，提高合理预算或稍后续跑。
- 漏跑多日：`/new` 只提供当前批次，按下面的显式 API 恢复步骤处理，不能依靠它重建历史公告。
- 定时没有运行：检查 Actions 启用状态、默认分支、仓库活动和 GitHub 服务状态。

不要在两个机器上同时使用同一个生产状态副本发信。工作流内的并发锁不能阻止你的本地程序。

## 定时触发与备用补跑

主 cron 为 `30 1 * * *`（北京时间 09:30），备用 cron 为 `47 1-15 * * *`（09:47–23:47 每小时一次）。二者均通过 `run --persist-outbox --daily-after 09:30` 执行。最早发送时间及当天日期使用配置时区；更换时区或时间时应同步修改这三处。

每日守卫先读取远端状态恢复的 outbox，按收件人检查当天已确认日报。空日报、普通手动 `send` 均计入，`delivery_test` 不计入；已发送的收件人不再抓取或调用模型。多人部分成功后，仅向尚未收到日报的收件人继续处理。pending 仍会阻断，备用任务不会绕过不确定发送状态。手动选择 `daily` 可验证此行为；手动 `send` 保留显式再次运行的能力。

outbox 增加兼容的 `sent_at` 可选列，与 sent 状态在同一事务中写入。旧记录回退使用其 created 时间，保留全部历史；迁移可重复执行。故障后人工 resolve 为 sent 的时间视为确认时间。检查发生在每日处理前，SMTP 最终投递跨午夜的极端情况仍应结合邮件日期人工核查。

`health.json` / Actions Summary 记录目标时间、程序开始时的延迟秒数、跳过收件人数和跳过原因。GitHub 根本没有创建运行时，这些程序日志也无法产生，失败邮件同样无法触发。应先看 Actions 的 schedule 事件是否存在，再看 runner 开始时间、模型步骤、SMTP 和数据库状态。

备用触发仍依赖 GitHub，无法保证 09:30 准点或平台故障时必定补跑。需要严格准点时，可由独立外部调度器调用 workflow_dispatch 的 `daily` 模式；它与定时任务共用并发锁和每日守卫。

2026-10-26 排查发现：10-25 唯一 schedule 事件于 14:38:19 才创建，runner 在 3 秒后开始，14:38:37 发信成功；10-26 截至 10:14 无 schedule 记录。手动补跑 10:16:17 创建、10:17:39 发送 5 篇。证据与修复验证见[调度排查记录](schedule-validation.md)。

## 独立外部调度

同一 GitHub 平台内增加 cron 无法解决平台根本不创建运行的问题。可在自己持续在线的服务器上配置独立定时器，安装并登录 GitHub CLI，授权对目标仓库运行 Actions，每天北京时间 09:40 起按小时执行：

```sh
gh workflow run daily.yml --repo OWNER/REPO --ref main -f mode=daily
```

替换 `OWNER/REPO`，默认分支不是 main 时也修改 `--ref`。外部使用的令牌只需执行 Actions 的适当权限，不需要模型或 SMTP 凭据。调用本身只创建工作流；服务器仍需检查命令退出码及后续运行结果，在失败时独立告警。可用 `gh run list --repo OWNER/REPO --workflow daily.yml --limit 5` 查看运行记录。

外部调用与仓库定时任务使用同一并发锁、每日去重和发送前保护；已发送时不会额外调用模型或再次发日报。独立定时器需要由部署者实际启用，这段配置不会自动创建定时器。它能绕过 GitHub cron 漏触发，仍无法保证 GitHub Actions 整个平台或邮件服务故障时准点送达。

## 状态写入失败后的恢复

GitHub 发送模式先保存 `prepared`（确定未调用 SMTP），再保存 `pending`（准备调用 SMTP）并允许发送。任一发送前步骤失败会清除本地未发送记录并尽力同步远端，最终状态保存仍会重试。恢复后的 `prepared` 可安全清理；旧版 `pending` 仍需人工核查。若远端 pending 已写入后进程被强制终止，即使尚未来得及调用 SMTP，也不能证明送达结果，仍保留人工确认。SMTP 明确拒绝发件人、收件人或 DATA 可安全重试；超时、断线等结果不确定的失败保留 pending。发送后最终 `Persist state` 失败时，远端至少保留 pending。不要直接重复发送：先下载 Artifact，核查收件箱与发送状态。数据库位于 `.state/digest.sqlite3`，报告位于 `output/`。本地不带 `--persist-outbox` 的运行没有这个远端前置保证。

在一个临时、独立目录克隆仓库的 `digest-state` 分支，使用 Artifact 中的数据库替换 `digest.sqlite3`，检查数据库中的发送记录 / 待确认记录，再提交并推送到状态分支。不要把数据库放到主分支。恢复时确保没有其他每日任务正在运行。

首次创建状态分支就失败时，可以在临时仓库建立名为 `digest-state` 的空分支，放入备份数据库后推送。数据库是否为最新记录不确定时，先检查收件箱，再选择 resolve。请保留备份直到恢复验证完成。

工作流读取不到现有分支时会停止。`ls-remote` 明确返回“分支不存在”才按首次运行处理；连接故障不清空已有历史。

## 停机与补抓

日常默认从 `/list/<category>/new` 读取完整的当前公告，包含新提交、跨分类与修订。分页日期、分区数量、总数和 ID 一致性均检查，不允许静默截断；跨分类是否读取由 `include_cross_lists` 控制。公告日期不等于首次提交日期。

`/new` 没有历史批次，`source = "new"` 必须搭配 `catch_up = false`。连续漏跑多日时，可先在 Actions 运行 `recover_preview`（窗口 1–31 天且不超过缓存保留天数），检查报告后运行 `recover_send`。这使用公开 API 的**首次提交日期窗口**，不代表精确公告历史，尤其不能完整恢复早年论文的新跨分类或修订；必要时人工核对。日常任务不调用 `/recent`。旧配置的 `source = "latest"` 仅为兼容保留，默认及推荐配置已全部切换到 `new`。

新提交与跨分类按论文 ID 去重；修订稿按 arXiv 明确版本（如 v2）去重。发送确认在同一事务中保存论文与版本记录；未确认发送不记为已发。旧数据库保留原有论文级去重；旧记录没有版本信息时，首次观察到的修订按新规则处理，不猜测过去发过哪个版本。已发送 v1 不阻止 v2，同一 v2 不因改变兴趣或评分权重而重发。元数据补查和机构补评同样区分修订版本。

三部分统一通过相关性和机构门槛，再按综合分选全局 Top K，默认总计最多 15 篇，没有最低篇数或分区保底名额。邮件按新提交、跨分类、修订顺序展示，各部分没有入选时说明为空。修订稿展示版本和更新时间，摘要只基于该版本摘要，不推测具体版本差异。成功投递后，本批其余候选标记已处理；需要后续补查的未发送论文仍由队列恢复。

显式 API 恢复不需要重置 `/new` 的检查点。`reset_checkpoints` 仅供旧版 latest 模式迁移恢复使用。RSS 与 API 仍保留为高级显式输入，日常默认不使用它们进行公告发现；API 在 `/new` 流程中只负责补全标题、摘要、作者、分类及版本。

## 元数据补查与诊断

已找到项目链接和有来源的署名机构时通常缓存 30 天；缺项目或未提取到机构时默认仅缓存 24 小时。作者是否逐个对应不影响完整性。缓存键包含提取策略、arXiv 版本/更新时间、摘要和模型配置；来源按版本固定，避免旧缓存搭配新 PDF。v7 会重新核查旧 v5/v6 机构结果，以免不完整机构清单跳过 PDF。PDF 暂不可读的部分结果同样使用短缓存。

未入选且尚未发送、机构缺失或 PDF 暂不可读的候选进入持久化补查队列：默认 24 小时后再查，每轮最多 20 篇、最多查找 3 次（含首次）。离开最新批次仍可补查。机构清单已完成本轮来源核查则清除旧补查记录，不为作者对应关系重试。名单外机构评估另有持久化补评队列，见[机构排序说明](ranking.md)。重复运行同份缓存不消耗尚未到期的次数；已发送论文不因此重发。仅缺项目链接不会形成持续补发队列。

需要单独核查时选择 `inspect` 并给出 1–5 个 ID，下载 `metadata.json`。该模式使用真实 DeepSeek，保留机构数量、来源和字段状态、更新缓存，但不做 JEV 判断、不发送、不推进公告或已处理历史。CLI 对应 `inspect --refresh 2508.08241 2606.03985`。日报 / 元数据 JSON 的 schema_version 为 2，完整性改用 `institutions_found` / `institution_count`；`affiliations[].authors` 只保留以兼容旧数据，新提取不输出作者对应。

单独验证邮箱选择 `delivery_test`（CLI `test-email`），会明确发一封联调测试邮件，使用与日报相同的认证、远端 pending 保存、SMTP 与确认流程。测试 outbox 不含论文 ID，所以不会改变真实论文的已发送/已处理历史；现有 pending 仍会阻止测试，不能用它绕过待确认记录。

## 预算与健康信息

预算按每次真实 HTTP 尝试计数，包含网络重试和 JSON 输出重试。JEV 筛选、DeepSeek 机构提取、摘要分别统计；命中本地缓存不计调用。`usage.json` 中 reported tokens 是服务商实际返回量，budget tokens 是实际量或未知时保留的估计，不能把未知当零。

调用次数上限严格受控。Token 在并发调用前预留，响应后结算；请求体字节数和最大输出用于保守估计。若估计已超剩余额度，即使实际可能较小也会终止本轮；已经在途的请求无法撤回，服务商隐藏 tokenization 也无法预先精确限制。超限后不开始新调用，也不发日报。系统不假定美元费用或服务商价格。

认证、权限、余额错误或预算耗尽不能被元数据“尽力补充”逻辑吞掉。异常通知只是提醒任务未完整结束；邮件可能已经被服务器接受，按 pending 流程核实后再重试。

## 隐私、保留与空间

模型缓存按 cache_days 清理；已发送 / 已处理 ID 长期保留。SQLite v5 原地迁移 v1/v2/v3/v4，保留所有发送历史和旧 pending，包含 prepared 阶段、机构补评队列、已发送版本表和学习到的机构及别名名单。升级前保留 Artifact；旧代码会拒绝 v5 状态，不要回退旧版本后继续使用新状态发送。SQLite 保存论文摘要、模型结果和地址哈希。Git 历史仍然包含曾提交的数据；需要彻底移除敏感信息时，按 GitHub 官方流程清理历史并撤销泄露凭据。

`.state/institutions.json` 是自动机构名单的可读导出，与数据库一同保存到状态分支和恢复 Artifact。`uv run arxiv-digest institutions` 可从数据库重新导出；确定的机构/简称长期保留，未核实中性意见仍按缓存期限重查。覆盖自动分数请编辑人工规则，完整行为见[机构名单扩充](ranking.md#自动扩充机构与简称名单)。

状态分支持续产生二进制提交，长期运行可增长仓库体积。维护者可在备份后压缩数据库 / 归档状态分支历史；不要删除当前发送记录。
