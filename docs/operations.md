# 运维与恢复

## 日常检查

在 Actions 查看 Daily arXiv Digest 的运行结果和自动生成的运行摘要。每次处理记录 `health.json`、`usage.json`，失败时也写出。发送模式失败可按 `notifications.email_on_failure` 向原收件人发异常通知；预览、inspect 永不发邮件。SMTP 自身故障时异常信也可能发不出，GitHub 失败记录仍是必要的第二条检查渠道。

- HTTP 401 / 403：检查相应 Secret、模型权限和服务地址。
- HTTP 402：检查服务商额度。
- HTTP 429 / 5xx：系统会有限重试，耗尽后失败，稍后重跑。
- 候选超过上限：减少分类或窗口，或提高 `max_candidates`。不会静默截断。
- 摘要 JSON 不完整：检查模型是否支持 JSON Output，或提高 max_tokens。
- SMTP 登录失败：核对服务器、安全模式、用户名与授权码。
- 待确认发送：先检查收件箱和垃圾箱，再执行 resolve。
- 预算耗尽：运行保持失败、不发日报；成功调用已缓存。检查 `usage.json`，提高合理预算或稍后续跑。
- 公告断档超出 recent 范围：不会自动猜测公告日，按下面的显式恢复步骤处理。
- 定时没有运行：检查 Actions 启用状态、默认分支、仓库活动和 GitHub 服务状态。

不要在两个机器上同时使用同一个生产状态副本发信。工作流内的并发锁不能阻止你的本地程序。

## 状态写入失败后的恢复

GitHub 发送模式先远程保存 pending，再允许 SMTP DATA。若预保存失败，日报发送被阻断；若发送后最终 `Persist state` 失败，远端至少保留 pending。不要直接重复发送：先下载 Artifact，核查收件箱与发送状态。数据库位于 `.state/digest.sqlite3`，报告位于 `output/`。本地不带 `--persist-outbox` 的运行没有这个远端前置保证。

在一个临时、独立目录克隆仓库的 `digest-state` 分支，使用 Artifact 中的数据库替换 `digest.sqlite3`，检查数据库中的发送记录 / 待确认记录，再提交并推送到状态分支。不要把数据库放到主分支。恢复时确保没有其他每日任务正在运行。

首次创建状态分支就失败时，可以在临时仓库建立名为 `digest-state` 的空分支，放入备份数据库后推送。数据库是否为最新记录不确定时，先检查收件箱，再选择 resolve。请保留备份直到恢复验证完成。

工作流读取不到现有分支时会停止。`ls-remote` 明确返回“分支不存在”才按首次运行处理；连接故障不清空已有历史。

## 停机与补抓

默认 latest + catch_up 按每个收件人、分类的成功公告检查点，补抓 recent 页面里可验证的后续批次。首次无检查点只取最新批；预览、预算失败、摘要失败或发送结果不确定都不推进。正常无匹配也会推进。不同分类更新节奏不同，不共享一个最大日期，避免漏掉较慢分类。

recent 的历史覆盖有限（通常只有近期几批），且月列表没有可靠日公告边界。早于可验证范围或超过 `catch_up_max_days` 时，任务明确失败并标记 `recovery_required`。

显式恢复流程：

1. Actions 选择 `recover_preview`，`recovery_days` 设置 1–31（不得超过 `retention.cache_days`），检查恢复窗口、候选和报告。
2. 核对后选择 `recover_send`，使用同样窗口。该模式按 API **提交日期**取公开论文，复用历史，仍有预算和远端 pending 保护。
3. 确认覆盖了需要的论文后，选择 `reset_checkpoints`。它只清当前 EMAIL_TO 与分类的公告检查点，**保留发送、已处理和待确认历史**；下一次 latest 从最新公告重新建立检查点。

API 提交窗口不等于精确公告历史，尤其不能保证恢复很久以前提交、最近才 cross-list 的全部论文；需要时人工补查分类月列表。程序不会宣称这一恢复是无遗漏的公告重建。

本地等效命令：`run --dry-run --recovery-days 7`、`run --recovery-days 7`、确认后 `reset-checkpoints`。GitHub 推荐用以上工作流模式，避免本地与远端状态分叉。

默认一次运行选窗口内的 Top K，成功后整批候选标记已处理，不会把未入选部分每天继续补发。若需要补发更多论文，应在恢复运行前提高 top_k（最多 100），或更改筛选参数以生成新配置指纹。已发送论文仍不会重复。

RSS 模式仅最近一次公告，适合低调用量的当天订阅；不适合多天停机后的补抓。

## 元数据补查与诊断

已确认完整资料通常缓存 30 天；缺项目、部分作者未映射或来源暂不可用的资料默认仅缓存 24 小时。缓存键包含提取策略、arXiv 版本/更新时间、摘要和模型配置；来源按版本固定，避免旧缓存搭配新 PDF。

未入选且尚未发送、机构不完整的候选进入持久化补查队列：默认 24 小时后再查，每轮最多 20 篇、最多查找 3 次（含首次）。离开最新批次仍可补查。重复运行同份缓存不消耗尚未到期的次数；已发送论文不因此重发。仅缺项目链接不会形成持续补发队列。

需要单独核查时选择 `inspect` 并给出 1–5 个 ID，下载 `metadata.json`。该模式使用真实 DeepSeek、保留状态和覆盖率、更新缓存，但不做 JEV 判断、不发送、不推进公告或已处理历史。CLI 对应 `inspect --refresh 2508.08241 2606.03985`。

## 预算与健康信息

预算按每次真实 HTTP 尝试计数，包含网络重试和 JSON 输出重试。JEV 筛选、DeepSeek 机构提取、摘要分别统计；命中本地缓存不计调用。`usage.json` 中 reported tokens 是服务商实际返回量，budget tokens 是实际量或未知时保留的估计，不能把未知当零。

调用次数上限严格受控。Token 在并发调用前预留，响应后结算；请求体字节数和最大输出用于保守估计。若估计已超剩余额度，即使实际可能较小也会终止本轮；已经在途的请求无法撤回，服务商隐藏 tokenization 也无法预先精确限制。超限后不开始新调用，也不发日报。系统不假定美元费用或服务商价格。

认证、权限、余额错误或预算耗尽不能被元数据“尽力补充”逻辑吞掉。异常通知只是提醒任务未完整结束；邮件可能已经被服务器接受，按 pending 流程核实后再重试。

## 隐私、保留与空间

模型缓存按 cache_days 清理；已发送 / 已处理 ID 长期保留。SQLite v2 原地迁移旧 v1 数据并保留 pending，增加检查点和补查队列；升级前保留旧 Artifact，不要把 v2 状态交给只支持 v1 的旧代码运行。SQLite 保存论文摘要、模型结果和地址哈希。Git 历史仍然包含曾提交的数据；需要彻底移除敏感信息时，按 GitHub 官方流程清理历史并撤销泄露凭据。

状态分支持续产生二进制提交，长期运行可增长仓库体积。维护者可在备份后压缩数据库 / 归档状态分支历史；不要删除当前发送记录。
